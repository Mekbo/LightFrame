# 光影工坊 LightFrame · 增量补丁包使用说明

## 一、发版策略（先看这个）

从 **v1.0.0** 起，仓库采用「**一个完整首发包 + 后续增量补丁包**」的发布方式：

- **v1.0.0 完整安装包**（`光影工坊_一键安装包_v1.0.exe`，约 100 MB）：唯一的首发基线包，已内置公司局域网证书兼容修复 **和完整的增量更新通道（更新引擎 + 应用内安装 + 空闲自动重启）**。**全新安装的用户只需装这一次**，以后不用再下载完整包。
- **后续每个新版本**：只发布一个很小的**增量补丁包**（通常只有几 KB ~ 几百 KB）+ 本说明。已安装 v1.0.0 的用户在应用内一键安装即可，或按下面步骤手动替换文件，无需重装、不会丢失任何配置和素材。

> 简单说：**第一次装完整包，以后每次升级只打小补丁。**

**两种升级方式**

| 方式 | 怎么操作 | 适合 |
|---|---|---|
| **应用内安装（推荐）** | 管理员进「关于应用 → 系统更新」，点「**安装更新**」；或在「全局设置」把安装方式设为「**自动安装**」 | 日常升级，不用碰服务器文件 |
| **手动替换** | 按下面第四节的 6 步操作 | 应用内安装失败时的兜底方案 |

> 说明：v1.0.0 基准包已内置完整更新引擎，从新装到后续升级都不需要再手动注入 `app_updater.py`、`restart_helper.py` 等文件。局域网服务器上若仍是"没有更新功能的旧版"，请按文末《附：局域网旧版一次性升级到 v1.0.0 基准》操作一次。

### 应用内安装是怎么工作的（安全设计）

1. **安装 ≠ 重启**：补丁只覆盖 `app\backend\` 和 `app\static\` 下的程序文件。Windows 下 `.py` 文件不被进程锁住，所以**安装过程不停止服务、不影响正在执行的任务**。
2. **忙闲避让**：装好后应用会等任务队列清空（执行中 = 0 且排队中 = 0），并连续稳定一小段时间才重启。如果此刻有任务在跑，页面会提示「**目前有任务在执行，请空闲时间再重启应用**」，并持续等待，队列空了自动完成重启。
3. **不停机的重启**：后端启动一个独立的重启助手进程后主动退出，助手等它退出后用启动器的 `--autostart` 把服务拉起来。全程不需要手动结束 `python.exe`。
4. **双重校验 + 可回滚**：补丁包内每个文件带 SHA256，Release 另附 `SHA256SUMS.txt` 校验整包；覆盖前自动备份到 `config\update_backup\`，装坏了可在页面点「回滚」。
5. **两种模式**（管理员在「系统设置 → 全局设置」设置）：
   - **手动安装**（默认）：检测到新版本只提示，由管理员点「安装更新」。
   - **自动安装**：检测到新版本且队列空闲时自动下载安装；可再设「仅夜间 22:00–06:00」避开业务时段。
   - 两种模式的**重启**都由守护线程在空闲时自动完成，无需人工点。

## 二、补丁包里有什么

补丁包是一个 zip，解压后通常是这样的结构（路径相对「安装目录」）：

```
LightFrame_Patch_vX.Y.Z.zip
├── manifest.json                     ← 版本 + 每个文件的 SHA256（安装端校验用）
├── app\
│   └── backend\
│       └── services\
│           └── app_update.py        ← 要替换的文件（示例）
├── app\static\index.html
└── 更新说明.txt                      ← 这次改了什么、要注意什么
```

**关键原则**：补丁包里的 `app\...` 路径，就是相对于「安装目录」的真实路径。把补丁包解压后，按同样的相对路径，把文件覆盖到安装目录对应位置即可。`manifest.json` 不覆盖、只用于校验。

## 三、安装目录在哪

默认安装位置是：

```
C:\Program Files\光影工坊\
```

（如果安装时改过路径，以你当时选的位置为准。）下面几个路径会反复用到：

| 用途 | 路径 |
|---|---|
| 后端服务源码目录 | `安装目录\app\backend\services\` |
| 前端页面 | `安装目录\app\static\` |
| 启动器 / 管理器 | `安装目录\光影工坊.exe` |
| 配置文件 | `安装目录\app\config\` |

> 找不到安装目录？双击「光影工坊.exe」打开「启动设置 / 管理器」页面，里面显示了安装路径。

## 四、升级步骤（务必按顺序做）

### 第 1 步：停止服务
双击「光影工坊.exe」打开管理器 → 点「**停止**」。

### 第 2 步：结束残留进程（最关键，别跳过）
后端服务是不热加载代码的。只点「停止」有时旧进程还驻留在内存里，导致"替换了文件却没生效"。

- 按 `Ctrl + Shift + Esc` 打开任务管理器 → 「详细信息」
- 找到所有 **`python.exe`** 进程 → 全部右键「结束任务」

> 服务器版（如 Windows Server 2019）如果服务是开机自启的后台进程，这一步尤其重要。

### 第 3 步：备份（养成习惯）
把要被替换的原文件复制一份，例如把
`安装目录\app\backend\services\app_update.py`
复制成 `app_update.py.bak`。出问题可以直接改回来。

### 第 4 步：替换文件
把补丁包解压，按相对路径把文件复制到安装目录对应位置，选择**覆盖**。

例如补丁包里的 `app\backend\services\app_update.py`，就覆盖到
`安装目录\app\backend\services\app_update.py`。

### 第 5 步：重启服务
双击「光影工坊.exe」→ 点「**启动**」（或「重启」）。

### 第 6 步：验证升级成功
1. 浏览器打开应用，进入「关于应用 → 系统更新」。
2. 看「当前版本」是否已变成补丁的版本号（如 v1.0.1）。
3. 点「立即检查更新」，状态应显示「**已是最新版本**」。

看到新版本号，就说明升级成功了。

## 五、常见问题

**Q：替换了文件，版本号还是没变？**
A：99% 是第 2 步没做——旧进程还在内存里跑着老代码。回到第 2 步，结束所有 `python.exe`，再重启。

**Q：怎么确认新代码真的加载了？**
A：更新检查的错误信息里带一个构建标记（如 `[v1.0.0-base-20261116]`）。有标记 = 新代码已加载；没有 = 服务还没重启。

**Q：升级会丢配置 / 素材 / 任务记录吗？**
A：不会。补丁只替换程序文件，`config\`（配置/账号）、`space\`（素材空间）、产物目录都不动。但保险起见仍建议升级前备份 `config\` 目录。

**Q：装补丁时提示"文件正在使用，无法覆盖"？**
A：说明服务还在运行。回到第 1、2 步，彻底停服并结束 `python.exe` 后再替换。

**Q：应用内点「安装更新」后，页面一直显示"等待空闲后重启"？**
A：正常。说明有任务在执行或排队，应用会持续等待，队列清空后自动重启。也可以让管理员在队列空闲时点「立即重启生效」。若不想等，把安装方式设为「自动安装 + 仅夜间」可避开业务时段。

**Q：「安装更新」按钮是灰的？**
A：三种情况：当前已是最新版本；该 Release 没上传 `LightFrame_Patch_*.zip` 补丁包；或正在安装中。非管理员看不到这个按钮。

**Q：应用内安装失败怎么办？**
A：页面会显示具体错误（校验失败 / 下载失败 / 写入失败），失败会自动回滚，不会留下半个补丁。可按第四节手动替换，或点「回滚」还原。

## 六、给维护者：如何制作增量补丁包

用仓库自带的脚本，一条命令生成全部产物：

```bash
python installer/make_patch.py --version 1.0.1 \
  --notes "修复 xxx" --min-base 1.0.0 \
  --file backend/services/app_update.py \
  --file static/index.html
```

产出在 `output/patch_v1.0.1/`：

- `LightFrame_Patch_v1.0.1.zip` —— 主附件（**必须 ASCII 名**，应用靠 `LightFrame_Patch_` 前缀识别）
- `SHA256SUMS.txt` —— 第二个附件，内容是整包 SHA256
- `本版本更新说明.txt` —— 人工备查，不上传

zip 内部结构（路径相对安装目录）：

```
manifest.json                ← version / min_base / notes / files[path,sha256,size]
app/backend/services/xxx.py
app/static/index.html
更新说明.txt
```

**硬性约定**（安装端会强制校验，不合规会被拒绝并回滚）：

- 只允许 `app/backend/` 和 `app/static/` 下的文件；`config/`、`space/`、`data/`、`output/`、`runtime/`、exe 一律拒绝，也拒绝 `..` 越界路径和绝对路径。
- 不允许 `.json` / `.pyc` / `.pyo` 文件（`manifest.json` 由脚本自动生成，不受此限）。
- `manifest.json` 里每个文件必须有 64 位 sha256；`version` 必须与 Release 的 tag 一致。
- 单个文件 ≤ 8 MB、整包 ≤ 32 MB。
- **新增的 `.py` 文件也要放进 `--file`**（例如某次升级新增了 `app_updater.py`、`restart_helper.py`、`config.py`），否则装完补丁会因为找不到文件而禁用相关功能。更新引擎本身已随 v1.0.0 基准包内置，常规补丁无需重复下发。
- **改动了配置结构时，`backend/core/config.py` 必须一并进补丁**（例如 2026-11-18 去水印框选新增 `regions`/`per_file`/`algorithm` 字段），否则后端读到的是旧字段定义，新配置会被丢弃或忽略。默认配置由 `config.py` 的 `DEFAULTS` 定义，是字段真值来源之一。
- **`min_base`（最低基线）会被安装端强制校验**：补丁 manifest 里的 `min_base` 表示"构造这个补丁所基于的最低版本"。安装时若用户当前版本 **低于** `min_base`，会被拒绝并提示"跨度过大，请下载完整安装包"，防止把为高基线构造的补丁套到低版本上造成静默错乱。因此 `--min-base` 必须如实填写补丁所基于的基线版本（本基线为 `1.0.0`）；不填则跳过校验（仅用于兼容老补丁，新补丁必须填）。

### 多基线与跨版本升级纪律（重要）

补丁是**整文件覆盖**而非逐行 diff：它把清单里的文件整体替换成目标版本的最终内容。这个特性决定了跨版本升级的安全边界，务必遵守：

1. **每个补丁都必须从最初基线（v1.0.0）累积**。即补丁的 `--file` 清单要包含"从 v1.0.0 到目标版本之间所有变动过的文件"，`--min-base` 固定填 `1.0.0`。这样：
   - 从 v1.0.0 一路打补丁上来的用户 ✅ 安全
   - 从中间某个全新安装包（如 v1.5）装的用户 ✅ 也安全（他自己已是最新，补丁覆盖的是相同的最终内容）
   - 两者套用同一个补丁，结果一致。
2. **千万不要做"只含相邻版本变动"的增量补丁**（例如只打 v1.9→v2.0 的文件）。那样从旧版本直接跳上来的用户会缺失中间的变动，而 `min_base` 校验会（正确地）拦下他们并提示重装完整包——徒增麻烦。
3. **全新安装包不得单独升级 `runtime\` / exe / 安装目录结构**。补丁只覆盖 `app\backend\` 和 `app\static\`，碰不到 runtime、启动器 exe 和目录结构。如果某次全新包换了 runtime 版本，就会和"一路打补丁上来"的用户形成两种底座（版本号却相同），日后极难排查。**若必须升级 runtime / exe，须明确告知：所有用户都要重装完整包，不能再用补丁升级。**
4. **跨度过大时的正确引导**：当版本跨度很大、或涉及第 3 条的底座变更时，不要勉强发补丁，直接发布全新安装包并让用户重装；`min_base` 校验会自动拦住不满足条件的自动安装，页面提示用户下载完整包。

> 一句话：**补丁永远从 v1.0.0 累积、只动 backend/static、底座（runtime/exe）永不变**——守住这三条，跨版本升级就始终是安全的。

### 发版步骤

1. 同步版本号真值：`backend/services/app_update.py` 的 `APP_VERSION` / `RELEASE_DATE` / `CHANGELOG`，以及根目录 `VERSION`，两者必须一致。
2. 运行 `make_patch.py` 生成补丁包（可先加 `--dry-run` 检查文件清单）。
3. GitHub 新建 Release（tag = `vX.Y.Z`），**上传两个附件**：`LightFrame_Patch_vX.Y.Z.zip` 和 `SHA256SUMS.txt`。
4. 推 main + tag，确认 `releases/latest` 指向这个新版本、raw `VERSION` 已更新。
5. Release 说明里引用本文档，并写明本次改动、是否需要重启。

> 发版一致性清单、证书库差异等更多经验，见 `docs/光影工坊_项目复盘经验_v1.md`。

## 附：局域网旧版一次性升级到 v1.0.0 基准

如果局域网服务器跑的还是**没有更新功能的旧版**（应用里看不到「安装更新」按钮、系统更新页没有补丁安装区），只需做一次带更新引擎的升级，之后就能走应用内一键/自动升级：

1. 拿到本次的 `LightFrame_Patch_v1.0.0.zip`（含 6 个程序文件：`app_update.py`、**新增** `app_updater.py`、**新增** `restart_helper.py`、`main.py`、`config.py`、`index.html`）。
2. 按第四节步骤操作：停服 → **结束所有 `python.exe`**（关键，否则替换不生效）→ 备份 `config/` → 解压按 `app\...` 相对路径覆盖文件 → 重启服务。
3. 验证：进入「关于应用 → 系统更新」，应看到「📦 增量补丁包安装」区；错误信息里的构建标记为 `[v1.0.0-base-20261116]` 即代表新代码已加载。

> 旧版服务器若连证书兼容修复也没有（检查更新报 `CERTIFICATE_VERIFY_FAILED`）：本次的 `app_update.py` 已含三级证书降级，替换后一并解决。完成后建议把服务器的 `VERSION` 与 `app_update.py` 的 `APP_VERSION` 都确认为 `1.0.0`，避免版本号不一致导致反复提示「发现新版本」。
